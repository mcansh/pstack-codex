### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, many subagents over time, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Read the [Codex runtime contract](../../codex-runtime.md). Run the program with the agent tools actually exposed in this session, using only their supported arguments. Keep state in an available, authorized project store or a gitignored `.pstack/orchestrate/<project-slug>/notes.md` in the project. Record standing orders, owners, branches, PRs, current head SHAs, verdicts, evidence pointers, and blockers. Include the standing orders in every kickoff and follow-up. Do not use the removed `orch` CLI, build orchestration scripts, or run polling loops. Pass needed reports in kickoffs rather than acting as a message or status relay between workers.

Use PR and CI event subscriptions only when exposed and authorized. Otherwise check live state at session checkpoints with available forge tools. This playbook supplies no persistent tracker, unattended wake, scheduler, or remote agent service. If a required lane needs an unavailable capability, mark it blocked and leave a durable handoff rather than claiming it ran.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to the authorized landing or handoff. Only the owner pushes, rebases, or retargets it, within the user's grant. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call and with authorization. Serialize stack topology changes across owners. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners. Neither this playbook nor a verifier's pass grants permission to publish, merge, deploy, delete, send messages, or change settings.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including the in-scope upstream reports it depends on. Workers cannot be assumed to see their siblings. Give each writer an exclusive worktree or scope; spawning does not isolate it. Use remote execution only through an exposed, documented, authorized API. If a separate VM is required but unavailable, block that lane. Local runtime checks, simulators, and local-only auth need an available local driver. Read only the active conversation or explicitly supplied in-scope history; never discover private transcripts by scanning session directories.
- **Inherit the parent model and effort.** Read `~/.config/pstack/codex-models.md` if present. Use an explicit role override only when configured by the user and supported by the spawn schema. Report an unavailable choice and inherit the parent; never construct model suffixes or silently switch vendors.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Use at most three levels, and fewer when the session's nesting limit requires it. Bound total in-flight agents by the actual session capacity, including verifiers and other tracks. Start the next worker as each finishes instead of waiting on a whole batch. If delegation is unavailable or prohibited, do useful sequential preparation, disclose reduced independence, and keep independent-verification gates blocked.
- **Transfer built state explicitly when new work needs it,** such as a checkout, uncommitted changes, or a running process. Fork only if the host tool supports it and ownership stays exclusive; otherwise give a fresh worker a consolidated handoff. Resume or message a worker only for a follow-up that needs its retained state, not to check on it. Use a read-only status tool or current artifacts for liveness; transcript timestamps are not proof. After a restart, re-read the handoff and verify agent status and PR heads. Never assume local or remote agents survived.
- **Each PR gets a verifier that is not its author.** A different model family is optional, only when explicitly configured and supported. An independent same-model reviewer is not multi-model evidence. The owner merges only when authorized and after an independent pass at the current head. If independent review is unavailable, the gate stays blocked.
- **Start with one unit.** Take it through kickoff, owner, verifier, and authorized landing or handoff before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a supported runtime check, or an artifact. It also names the goal, the paths the worker may and may not write, its exclusive workspace, and the actions it must not take. Prompt-level read-only scope is not a sandbox guarantee. If you cannot name the evidence, the unit is not scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Missing runtime proof is unverified, not a pass. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with available forge tools, not the worker's last report. Record the current head and verdict in the project notes. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by available agent status and current artifacts, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a corrected tool call after a schema error. Model changes still follow the configured role policy. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an action outside the grant, a required approval, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" do not need a new question when already authorized. Do not treat silence as approval.

**Reply:** what landed against the goal, each PR's live state and current-head verdict with its link, what was dropped or blocked and why, capabilities and evidence still unverified, the durable handoff path, and the decisions waiting on the user.
